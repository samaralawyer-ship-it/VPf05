# ТЗ: цепочка генерации модуля из текстового описания

Учебный проект по уроку **VPf05 «Цепочки запросов (Chains)»**.
Версия 3.0. Документ можно приложить к сдаче как `docs/chain-spec.md`.

## 1. Цель

Собрать цепочку из четырёх звеньев на LangChain, которая по короткому текстовому
описанию генерирует рабочий Python-модуль, проверяет его **машинно** и оставляет
после каждого шага проверяемый артефакт.

Демонстрационная задача: описание модуля, который читает `inputdata/orders.csv`
с колонками `category, amount`, считает сумму и количество заказов по категориям
и пишет `outputdata/output.json` плюс наглядный `outputdata/output.txt`.

## 2. Принципы, заложенные в проектирование

Эти принципы обсуждались до написания ТЗ и определяют, почему требования именно такие.
Каждый пункт — «что делаем» и «почему».

| № | Принцип | Как применён |
|---|---|---|
| 1 | **Роль — это точка зрения и приоритет, а не регалии** | В промптах нет «ты опытный программист с 10 годами стажа». Вместо этого: «ты пишешь код под запуск, а не под чтение». Роль задаёт, что считать важным |
| 2 | **Контекст — это факты, а не прилагательные** | В контекст попадают только проверяемые факты: «только стандартная библиотека», «файлы в inputdata». Фразы вида «качественно» и «профессионально» запрещены: они не меняют результат |
| 3 | **Формат задаётся схемой, а не описанием** | Каждое LLM-звено возвращает JSON по схеме из раздела 5. Схема проверяется кодом, а не глазами |
| 4 | **Проверка — это измерение, а не мнение** | Звено 4 не спрашивает модель «есть ли ошибки». Оно делает `py_compile` и запуск. Мнение модели о своём же коде — не проверка |
| 5 | **Артефакт после каждого шага** | Звенья 1–2 пишут JSON, звено 3 — файлы, звено 4 — протокол. Любой шаг можно перезапустить отдельно |
| 6 | **Критерий приёмки без эталонного ответа** | Не «какой код правильный», а «какая команда и какой наблюдаемый признак». Эталона для новой задачи не существует, признак — существует |
| 7 | **Границы и открытые вопросы — явно** | В ТЗ есть раздел «не входит» и поле `open_questions` в артефакте анализа. Недописанное называется вслух, а не прячется в контекст |
| 8 | **Воспроизводимость** | Модель, `temperature`, версия промптов и `run_id` пишутся в лог. Удачный прогон можно повторить |

## 3. Почему цепочка, а не один промпт

Дробим только тогда, когда промежуточный результат:

- является артефактом, который читает следующий шаг;
- проверяется гейтом до дорогой операции;
- требует других параметров, инструмента или модели.

| Звено | Артефакт | Почему отдельно |
|---|---|---|
| 1. Анализ | `01-analysis.json` | список функций и ограничений проверяется до генерации кода |
| 2. Инструменты | `02-tools.json` | фиксируем, что разрешено; запрет `pandas` дешевле проверить здесь, чем переделывать код |
| 3. Реализация | `03-code/*.py` | продукт |
| 4. Проверка | `04-check.json`, `report.md` | машинный гейт, не мнение модели |

Обратная сторона: каждый переход сжимает информацию. Четыре звена оправданы только потому,
что каждый шаг оставляет нужный артефакт. Если бы звенья 1–2 не проверялись, цепочку
стоило бы свернуть в два шага — «план и код».

## 4. Реализация на LangChain

Цепочка собирается на LCEL: `prompt | model | parser`.

- `langchain-core` — `ChatPromptTemplate`, `StrOutputParser`, `JsonOutputParser`, `RunnableLambda`.
- `langchain-openai` — `ChatOpenAI` с `base_url` провайдера (DeepSeek совместим с OpenAI API).
- Версии пакетов фиксируются в `requirements.txt` после проверки прогона.
- Разбор ответа: `JsonOutputParser`; при ошибке разбора — один повтор с текстом ошибки
  и требованием вернуть только JSON.

Звено 4 в LangChain не реализуется: это обычный Python-код проверки.

## 5. Реестр промптов

Для каждого LLM-звена промпт описан карточкой: роль, контекст, задача, формат вывода.

### Звено 1 — анализ

- `prompt_id`: `chain.analysis`, `version`: 1
- **Роль:** аналитик, который превращает пожелания в проверяемые требования.
- **Контекст:** описание модуля от пользователя; ограничение «только стандартная библиотека».
- **Задача:** выделить функции, входы, выходы, ограничения и открытые вопросы.
- **Формат:** JSON по схеме `01-analysis.json`.

### Звено 2 — инструменты

- `prompt_id`: `chain.tools`, `version`: 1
- **Роль:** инженер, который выбирает минимальный набор средств.
- **Контекст:** артефакт анализа; правило «чем меньше зависимостей, тем лучше».
- **Задача:** выбрать библиотеки, перечислить запрещённые и объяснить выбор.
- **Формат:** JSON по схеме `02-tools.json`.

### Звено 3 — реализация

- `prompt_id`: `chain.code`, `version`: 1
- **Роль:** программист, который пишет код под запуск, а не под чтение.
- **Контекст:** артефакты звеньев 1–2; при ремонте — ещё и текст ошибки из звена 4.
- **Задача:** написать `main.py`, `main_test.py`, `README.md`.
- **Формат:** три файла в `03-code/`, код без пояснений в чате.

## 6. Схемы артефактов

`01-analysis.json`

```json
{
  "module_name": "orders_summary",
  "functions": ["load_orders", "summarize", "write_json", "write_txt"],
  "inputs": [{"name": "inputdata/orders.csv", "format": "csv", "columns": ["category", "amount"]}],
  "outputs": [{"name": "outputdata/output.json", "format": "json", "schema": {}}],
  "constraints": ["только стандартная библиотека", "без сети"],
  "open_questions": ["что делать с пустым файлом"]
}
```

`02-tools.json`

```json
{
  "libraries": ["csv", "json", "pathlib", "argparse"],
  "forbidden": ["requests", "pandas"],
  "data_storage": "файлы в inputdata/outputdata",
  "notes": ["pandas запрещён: модуль должен работать без установки зависимостей"]
}
```

`04-check.json`

```json
{
  "checks": [
    {"name": "py_compile", "command": "python -m py_compile main.py main_test.py", "status": "pass", "output": ""},
    {"name": "run_test", "command": "python main_test.py", "status": "pass", "output": "..."},
    {"name": "artifact_exists", "command": "проверка файла outputdata/output.json", "status": "pass", "output": ""},
    {"name": "envelope_schema", "command": "проверка ключей JSON-конверта", "status": "pass", "output": ""}
  ],
  "verdict": "pass",
  "repair_attempts": 0
}
```

## 7. Проверка и цикл ремонта

Порядок:

1. `python -m py_compile main.py main_test.py` — синтаксис;
2. `python main_test.py` — запуск, таймаут 60 секунд;
3. существует и валиден `outputdata/output.json` — это JSON-конверт целиком, бизнес-данные лежат внутри поля `output`;
4. ключи JSON-конверта: `run_id`, `module`, `version`, `status`, `output`, `stats`.

Если проверка провалилась — **один** повтор звена 3 с текстом ошибки в контексте.
Второй провал — статус `failed`, отчёт сохраняется, цепочка останавливается.

Правила, без которых цикл теряет смысл:

- критерии проверки в коде — **неизменны**; звено 3 не может их править;
- конфликт «ТЗ против проверки» — стоп и дефект в отчёте, а не тихая правка.

## 8. Воспроизводимость

| Параметр | Значение |
|---|---|
| Модель | `deepseek-flash`, режим мышления выключен |
| `temperature` | 0.2 (звенья 1–2), 0.1 (звено 3) |
| `max_tokens` | 800 / 800 / 4000 |
| Повторы | 2 на коды 429 и 5xx, с паузой |
| Ключ | `DEEPSEEK_API_KEY` из `.env` |

В `chain.log` пишется: `run_id`, `prompt_id`, версия промпта, модель, `temperature`,
`max_tokens`, расход токенов, время шага.

## 9. Интерфейс запуска

```
python chain.py --input examples/desc.txt
python chain.py --input examples/desc.txt --run-id test1
```

Коды возврата: `0` — все проверки прошли, `1` — провал проверки, `2` — ошибка конфигурации.

## 10. Критерии приёмки

| № | Критерий | Как проверить | Наблюдаемый признак |
|---|---|---|---|
| 1 | Цепочка запускается | `python chain.py --input examples/desc.txt` | код 0 |
| 2 | Артефакты всех звеньев есть | `ls runs/<run_id>` | 4 файла или папки |
| 3 | Сгенерированный код компилируется | `python -m py_compile runs/<id>/03-code/main.py` | код 0 |
| 4 | Сгенерированный модуль работает | `cd runs/<id>/03-code && python main_test.py` | код 0 и `outputdata/output.json` |
| 5 | JSON-конверт соответствует схеме | `04-check.json` | `envelope_schema: pass` |
| 6 | Провал действительно ловится | испортить `main.py` вручную, перезапустить проверку | `verdict: fail`, ремонт или остановка |
| 7 | Параметры зафиксированы | `grep model runs/<id>/chain.log` | модель, temperature, версия промпта |

Критерий 6 важен отдельно: он доказывает, что проверка не декоративная.

## 11. Что не входит

- модули с базой данных, сетью и внешними API;
- оценка «красоты» кода человеком;
- веб-интерфейс, параллельные прогоны, кэширование;
- автономный агент, который сам решает, сколько шагов делать;
- несколько моделей и маршрутизация между ними.

## 12. Бюджет сложности

Проект учебный, поэтому сложность не наращивается. Правило для любого нового элемента:
он должен усиливать проверяемость или воспроизводимость, а не «интересность».

Что уже есть и считается достаточным:

- четыре звена, LangChain LCEL, JSON-схемы, машинная проверка, один ремонт, лог с параметрами.

Что не добавляем, даже если умеем:

- векторную память, RAG, инструменты с побочными эффектами;
- оркестратор с динамическим выбором шагов;
- панель мониторинга и базу для прогонов.

## 13. Что сдаём и что попадает в репозиторий

Формат сдачи — **репозиторий GitHub**.

В репозиторий входят:

- `chain.py`, `prompts/` (три промпта по реестру), `examples/desc.txt`;
- `requirements.txt`, `.env.example`;
- `README.md` — логика шагов, обоснование, как проверять;
- `ТЗ-VPf05-цепочка.md` — это ТЗ, включено как проектная документация;
- `.gitignore`.

Не входят:

- страница урока (`*.html`, `*_files/`) — в `.gitignore`;
- `runs/` — сгенерированные артефакты прогонов;
- `.env` — секреты;
- `__pycache__/`, `.venv/`, `.log`.

## 14. Принятые решения

1. **Сдача** — репозиторий GitHub, скриншоты и лог не обязательны.
2. **Демонстрационный прогон с поломкой не делаем.** В README есть раздел
   «Как проверить, что гейт не декоративный»: команда порчи кода и ожидаемый результат.
3. **Страница урока в `.gitignore`**, ТЗ — в репозитории.
